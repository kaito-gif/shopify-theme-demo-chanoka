### トラブル対応事例を書くときの制約

このページで最も効く節になる見込みだが、同時に最も情報漏れのリスクが高い。

- 判断基準は「**技術記事に書いても違和感がない粒度か**」。満たせば個別案件の
  記述ではなく一般的な知見として成立する
- クライアント名・ストア名・ドメインに加え、**業種・規模・時期も書かない**
  （組み合わせから特定されうる）
- 「〇〇なサイトで」ではなく「**〇〇という事象が起きたときは**」と書く
- 安全な例: 「本番反映後に旧デザインが表示される → configキャッシュ残存」
- 注意が必要な例: 移行や公開の文脈を1語でも足すと特定に近づくものは、
  **事象と対処だけで止める**

### 未決の事項

- 経験年数をどの名義の数字で出すか。問い合わせ時の口頭説明と食い違うと信頼を
  落とすため、先に決めてから書く
- 価格は公開ページに載せない。出すかどうかはデモストア公開後の反応を見て判断
- ブランド名をパッケージ画像に合成するか、無地のままにするか

## 構造化データの検証（2026-08-02）

`sections/faq-structured.liquid` が出力する FAQPage JSON-LD を
**Schema Markup Validator（`validator.schema.org`）** で検証し、
エラー0件 / 警告0件。FAQPage 1件・Question 4件、各 Question に
`acceptedAnswer > Answer > text` が揃っている。

**リッチリザルトテストは使えない。** GoogleはFAQリッチリザルトを2026-05-07に
全サイトで廃止し、2026-06にリッチリザルトテストとSearch Consoleの
FAQレポートからも対応を外した（Search Console API は2026-08で終了）。
FAQPage 自体は schema.org の有効な型のままで、Googleはページ理解のために
引き続き解析すると明言しているため、マークアップは残す。
検証はリッチリザルトテストではなく `validator.schema.org` で行うこと。

ポートフォリオでの書き方に注意。「FAQリッチリザルトが出る」とは**書けない**。
「構造化データを正しく出力できる／Dawn標準では出ないものを補える」という
実装能力の証明として提示する。
